FIELD GUIDE · 01

로그에서 공격 확정을 주장하기 전에

2026-10-28 · 교육용 사례 · 합성 로그

웹 로그에 /admin?cmd=whoami 같은 요청이 보였다고 서버에서 명령이 실제 실행됐을까요? 대개 답은 ‘그 정보만으로는 알 수 없다’입니다. 요청이 도달했는지, 애플리케이션이 처리했는지, 운영체제 실행이 있었는지는 서로 다른 질문입니다.

1. 세 가지 판정 수준

수준관측 예시허용되는 결론
징후위험한 형태의 HTTP 요청의심 요청 관측
추론관련 응답·연속 요청·애플리케이션 이벤트공격 시도 및 진행 가능성 증가
확정요청과 인과적으로 연결된 실행·파일 생성 등 신뢰 가능한 독립 증거검증된 행위 범위 내에서만 확정

상태 코드 200만으로 성공을 확정하거나 404만으로 실패를 확정해서는 안 됩니다. 커스텀 에러 페이지, 인증 프록시, 비동기 작업, 캐시로 결과가 달라질 수 있습니다.

2. 합성 타임라인 사례

10:00:01 web  GET /admin?cmd=whoami  status=200 request_id=r7
10:00:02 was  route=/admin auth=denied request_id=r7
10:00:03 os   (corresponding execution event not observed)

이 경우 요청은 관측됐지만 애플리케이션이 권한을 거부한 흔적이 있고, 대응하는 명령 실행 기록은 확인되지 않습니다. 결론은 ‘명령 실행 확정’이 아니라 ‘의심 요청 관측, 실행 미확인’입니다. OS 기록이 없다는 사실만으로 실행이 절대 없었다고도 말할 수 없습니다. 수집 공백 가능성을 별도 조사해야 합니다.

3. 검증 체크리스트

  1. 각 로그의 수집 범위·시간대·시계 오차를 기록합니다.
  2. 요청 ID·프로세스·세션·신뢰 가능한 프록시 경로로 이벤트를 연결합니다.
  3. IP 주소만 같은 별개의 사용자를 하나의 공격자로 합치지 않습니다.
  4. 증거 누락과 수집 실패를 별도의 상태로 표현합니다.
  5. 증거의 원본 위치와 판정 규칙 버전을 보존하되 개인정보는 최소화합니다.
  6. 확정 판정에는 단계별 명시적 조건을 두고 반례 테스트를 실행합니다.

4. 테스트할 반례

같은 NAT IP를 공유하는 두 사용자, 상이한 시간대를 쓰는 서버, 중복된 요청 ID, 뒤늦게 들어온 OS 이벤트, 로드밸런서가 추가한 XFF 헤더를 각각 시험합니다. 정상/의심 사례를 함께 준비하고 사람이 정한 정답과 엔진 출력의 차이를 기록합니다.

5. 참조

MITRE ATT&CK는 기술·전술 분류를 위한 참조 체계입니다. ATT&CK 매핑은 행위의 확정 증거 자체가 아닙니다. NIST SP 800-61 Rev.3은 침해 대응 체계 설계에 참고할 수 있습니다.
