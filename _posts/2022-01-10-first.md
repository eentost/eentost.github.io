> 2026-09-23 전면 개정. 기존 게시 주소와 최초 게시일은 유지했습니다. 아래 사례와 수치는 교육용 합성 예제이며 실제 침해 사고나 운영 성과가 아닙니다.

보안 도구가 빨간 경고를 띄웠다는 기록만으로는 다음 사람이 같은 결론을 검증하기 어렵습니다. 무엇을 입력했고 어떤 설정으로 실행했는지, 경고가 무엇을 입증하는지 빠져 있기 때문입니다. 이 글은 EENTOST의 실습을 읽거나 자신의 분석 노트를 만들 때 사용할 **작은 증거 기록 양식**을 제안합니다. 목표는 전문가처럼 보이는 문장을 쓰는 것이 아니라 다른 사람이 결론을 반박하거나 재현할 수 있게 만드는 것입니다.

## 질문을 한 번의 비교로 줄이기

“이 파일은 안전한가?”는 한 번의 해시 계산으로 답할 수 없습니다. “이 두 바이트열은 같은가?”는 답할 수 있습니다. 아래에서는 줄바꿈 하나를 추가했을 때 SHA-256 결과가 변하는지 관찰합니다. 이 실험에서 해시 불일치는 악성 여부가 아니라 입력의 차이를 뜻합니다. 실행 파일을 내려받거나 실행할 필요가 없습니다.

Python 3 표준 라이브러리만 사용하는 코드를 `note_demo.py`로 저장하고 `python note_demo.py`로 실행합니다. `python --version` 출력도 노트에 적어 두면 환경 차이를 추적하기 쉽습니다.

```python
import hashlib

original = b"research-note"
copy = bytes(original)
changed = original + b"\n"
digest = lambda value: hashlib.sha256(value).hexdigest()
print("same_copy:", digest(original) == digest(copy))
print("newline_added:", digest(original) == digest(changed))
print("lengths:", len(original), len(changed))
assert digest(original) == digest(copy)
assert digest(original) != digest(changed)
```

```text
same_copy: True
newline_added: False
lengths: 13 14
```

같은 복사본을 먼저 비교하는 이유는 측정 절차 자체가 일관적인지 확인하기 위해서입니다. 변경본만 검사하면 “변경을 탐지했다”와 “실행 때마다 결과가 흔들린다”를 구별하기 어렵습니다. 마지막 두 검사는 위 관찰을 코드로 남긴 것입니다. 모든 가능한 충돌을 배제하는 수학적 증명은 아닙니다.

## 결과를 기록하는 실제 양식

| 기록 항목 | 이 실험에서 적을 내용 | 빠졌을 때 생기는 문제 |
|---|---|---|
| 질문 | 줄바꿈 추가가 해시 비교에 드러나는가 | 안전성 판정으로 과장하기 쉬움 |
| 입력 | UTF-8 텍스트를 가정하지 않는 명시적 바이트열 | 인코딩·줄바꿈 차이를 놓침 |
| 통제 조건 | 원본과 동일한 복사본 | 도구 자체의 일관성 확인 불가 |
| 변경 조건 | 끝에 LF 한 바이트 추가 | 무엇 때문에 결과가 바뀌었는지 모름 |
| 관찰 | 길이 13→14, 해시 비교 불일치 | 해석만 남고 증거가 사라짐 |
| 결론 범위 | 이 두 입력의 바이트가 다름 | 악성·유출 판정으로 확대될 수 있음 |
| 재검증 | 변경본을 원본으로 바꾸면 두 비교가 모두 참 | 실패 조건이 없는 성공 사례가 됨 |

기록 파일에는 실행 명령, 도구 버전, 입력 식별자와 출력 원문을 붙입니다. 스크린샷만 있으면 긴 출력의 앞부분이나 옵션이 잘릴 수 있으므로 텍스트 기록도 보존합니다. 실제 사건 자료에는 접근 권한과 보존 절차가 필요하며, 공개 글에는 실제 고객 로그나 비밀값을 사용하지 않습니다.

## 관찰에서 결론까지 한 단계를 더 적기

예를 들어 “해시가 바뀌었다”는 관찰입니다. “파일이 전송 중 손상됐다”는 가능한 설명 중 하나입니다. 편집기의 줄바꿈 변환, 다른 버전의 파일, 압축 해제 차이도 후보입니다. 따라서 노트에는 `관찰: 해시 불일치 / 가설: 전송 변형 / 대안: 생성 버전 차이 / 다음 확인: 원본 버전과 바이트 길이`처럼 네 칸을 남기는 편이 낫습니다.

반대로 해시가 같아도 원본 출처가 신뢰할 수 있는지, 파일을 실행해도 되는지는 별도 질문입니다. 서명 검증과 배포 경로, 실행 환경까지 확인해야 하는 문제를 체크섬 하나로 축소하지 않습니다. 관련 실험은 [SHA-256과 HMAC 비교]({% post_url 2026-03-04-cryptography-basics %})에서 이어갑니다.

## 실패한 재현을 숨기지 않는 방법

다른 환경에서 결과가 다르면 입력·환경·절차 중 하나씩 비교합니다. 동시에 여러 설정을 바꾸면 어떤 변화가 원인이었는지 알기 어렵습니다. 재현되지 않은 결과를 삭제하는 대신, 차이가 난 조건과 확인하지 못한 사항을 수정 이력에 남깁니다. 게시일을 새 날짜로 바꿔 과거 검증처럼 보이게 하지 않고 실제 개정일을 별도로 표시합니다.

이 양식은 법적 증거 보존 절차를 대체하지 않습니다. 작은 학습 실험에서 주장과 증거를 구분하기 위한 도구입니다. [NIST SP 800-86](https://csrc.nist.gov/pubs/sp/800/86/final)은 사고 대응과 포렌식 절차를 연결하는 참고 자료이며, 코드 API는 [Python hashlib 문서](https://docs.python.org/3/library/hashlib.html)를 기준으로 확인할 수 있습니다. 사이트 전체 작성 기준은 [편집 원칙](/editorial-policy/)에 공개합니다.
